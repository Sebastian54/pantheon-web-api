# Project Overview
**Name:** Pantheon - Admin Web Dashboard
**Domains:** `archer.software` (Frontend), `api.archer.software` (Backend)
**Purpose:** A centralized multi-tenant dashboard displaying analytics, command logs, and moderation data from remote Minecraft servers.

## Tech Stack Constraints
*   **Monorepo Tooling:** npm workspaces or Turborepo.
*   **Backend API (`/apps/api`):** Node.js, TypeScript, Fastify, Zod validation.
*   **Database:** PostgreSQL (with TimescaleDB extension for event logs), Drizzle ORM.
*   **Frontend (`/apps/web`):** Next.js (App Router), TypeScript, Tailwind CSS, shadcn/ui, Tremor for charts, Framer Motion.
*   **Authentication:** NextAuth.js (Auth.js), multi-provider — **Discord OAuth**, **Google OAuth**, and **email/password (Credentials)**, the last with optional **TOTP two-factor authentication**.

## UI/UX: Apple Liquid Glass Standards
The frontend must strictly adhere to Apple's Liquid Glass UI (macOS Tahoe / iOS 26) and Human Interface Guidelines. Use heavily layered `backdrop-blur`, fluid bubbles, thin semi-transparent borders, and a San Francisco system font stack.

## Authentication & Multi-Tenancy
*   **Web Users:** Three ways to sign in, all coexisting on the same `users` row: **Discord OAuth**, **Google OAuth** (both via NextAuth's `DrizzleAdapter`, linked through the standard `accounts` table — a user can hold both an OAuth account and a password simultaneously), and **email/password** via NextAuth's `CredentialsProvider` (`apps/web/src/lib/auth.ts`). Credentials sign-in additionally gates on two things OAuth sign-in never checks: `users.email_verified` (must be non-null — see Registration below) and, if enabled, a TOTP code. Both gates live entirely inside `CredentialsProvider`'s `authorize()` callback, so OAuth users are unaffected by them regardless of their own `email_verified`/`two_factor_enabled` values.
*   **Password storage:** `users.password_hash` (nullable — null means "OAuth-only account," which is also what `authorize()` checks to reject Credentials sign-in for those users). Hashed with bcrypt (`bcryptjs`, 12 rounds) via `lib/password.ts` in both `apps/web` (registration + login) and `apps/api` (mobile login) — pure-JS on purpose, avoiding native `node-gyp` bindings that would complicate the Docker cross-build.
*   **Email verification:** `users.email_verified` (pre-existing NextAuth-adapter column, timestamp, nullable) doubles as the "has this Credentials account confirmed its email" flag. `POST /register`'s server action (`app/register/actions.ts`) creates the user with it null, generates a random 32-byte hex token, and reuses the NextAuth-adapter's own `verification_tokens` table (`identifier` = email, 24h expiry) to store it — this is a bespoke verification flow, **not** NextAuth's built-in Email/magic-link provider (which isn't enabled); it just reuses that table's shape. `GET /verify-email` (a Route Handler, `app/verify-email/route.ts`) consumes the token, sets `email_verified = now()`, and redirects to `/sign-in`.
*   **Two-Factor Authentication (TOTP):** `users.two_factor_secret` (nullable) + `users.two_factor_enabled` (boolean, default false). Setup (`/settings` → `components/two-factor-settings.tsx` + `app/settings/security/actions.ts`) generates and stores a secret immediately but leaves `two_factor_enabled` false until the user proves possession by submitting one valid code back (`confirmTotpSetup`) — a half-finished setup never silently gates login. Disabling (`disableTwoFactor`) requires a currently-valid code too, not just a click-through confirmation. Verification uses `otplib`'s functional API (`verify()`, ±30s epoch tolerance for clock drift) via a small `lib/totp.ts` duplicated in both apps (same no-shared-package convention as `lib/password.ts`). **Web login:** `CredentialsProvider.authorize()` throws a distinguishable `TWO_FACTOR_REQUIRED` error when `two_factor_enabled` is true and no code was submitted; the client-side form (`components/credentials-sign-in-form.tsx`, calling `signIn(..., { redirect: false })`) catches that string and re-prompts for the code in the same form, then resubmits. **Mobile login:** `POST /api/v1/auth/mobile/login` returns `{ requiresTwoFactor: true, pendingToken }` instead of a full session token — `pendingToken` is a 5-minute NextAuth-JWT-encoded token carrying `{ sub: userId, pending2fa: true }`, exchanged via `POST /api/v1/auth/mobile/verify-2fa` for the real session token once the code checks out.
*   **Transactional email (Mailgun):** `lib/mailgun.ts` calls Mailgun's HTTP API directly via `fetch` with HTTP Basic auth (`api:<MAILGUN_API_KEY>`) — no SDK dependency, matching the existing no-SDK convention already used for Discord's REST calls (`apps/api/src/lib/discord.ts`). Duplicated independently in **both** apps (`apps/web/src/lib/mailgun.ts` and `apps/api/src/lib/mailgun.ts`, same no-shared-package convention as `lib/password.ts`/`lib/totp.ts`) since `apps/api` never calls into `apps/web` — each app's `/register` sends its own verification email. Used today for verification-link emails (`sendVerificationEmail`); `MAILGUN_API_KEY` / `MAILGUN_DOMAIN` (GitHub Student Pack credits) required in each app's own env, `MAILGUN_API_BASE` only needed to override to the EU region.
*   **Account ID:** `users.account_id` — an 8-digit numeric string (`varchar(8)`, unique-indexed, stored with no separator; UIs format it as e.g. "1234-5678" via `formatAccountId`/`format-accountId`-equivalent helpers), the human-shareable identifier for network invitations in place of the internal uuid. Generated app-side with a retry-on-conflict loop (`generateAccountId` + an `insertUserWithAccountId` wrapper, duplicated in `apps/api/src/lib/crypto.ts` and `apps/web/src/lib/account-id.ts` — same no-shared-package convention as everywhere else) at every user-creation path: `apps/api`'s Discord/Google/register mobile routes, and `apps/web`'s Credentials `/register` action plus a `createUser` override on the NextAuth adapter (the stock `DrizzleAdapter` has no idea `account_id` exists, so Discord/Google sign-ins through the *browser* would otherwise violate the column's `NOT NULL` constraint outright). Migration `0025` backfills existing rows (an `UPDATE ... WHERE account_id IS NULL` — safe as a one-shot for the handful of pre-existing accounts, not a retry loop) before adding the `NOT NULL` + unique index, since `ADD COLUMN ... NOT NULL` alone fails outright against a table that already has rows.
*   **Mandatory display name, nullable at the DB level:** `users.name` stays nullable in the schema — Discord/Google already set it from the provider's profile at sign-in, and `apps/api`'s mobile `/register` now requires it (`mobileRegisterBodySchema`'s `name` dropped `.optional()`), but pre-existing pre-this-change email/password accounts could still have a null one, and enforcing `NOT NULL` at the DB level would mean picking a value on their behalf. Instead, both apps close the gap client-side: **web** — `apps/web/src/proxy.ts` (Next 16's `middleware.ts`, renamed; defaults to the Node.js runtime here, so a direct DB read is safe) checks the signed-in user's current `name` on every request and redirects to `/complete-profile` if it's empty, for any path other than the auth/profile-completion pages themselves; **mobile** — the iOS app shows its own one-time "Complete Profile" screen on the same condition, backed by `PATCH /api/v1/users/me` (`{ name }`, Bearer-authenticated, always acts on the caller). `session.user.name` itself is re-derived fresh from the DB in the `session()` callback (not trusted from the JWT's cached `name` claim) for the same reason `networks` already is — otherwise the guard would stay blind to a just-completed profile until the token itself refreshed.
*   **Multi-tenancy model:** Network-first. A `network` is the team/tenant boundary, owned by one user (`networks.owner_id`) with per-network roles (`OWNER`/`ADMIN`/`MODERATOR`) assigned via `network_members`. OWNER/ADMIN have implicit access to every server in their network; MODERATOR needs an explicit `server_access_grants` row per server. There is no global role anymore — `users.role` and `user_servers` were removed in the cutover to this model (2026-08-09).
*   **Server claiming:** `servers.network_id` is nullable. `POST /api/v1/register` is an unauthenticated handshake with no way to know which network a freshly-booted server belongs to, so new rows land with `network_id = NULL` ("unclaimed"). A network OWNER/ADMIN claims an unclaimed server into their network from `/admin`.
*   **Bootstrapping:** A signed-in user with zero network memberships sees a "Create your network" prompt on `/` instead of the dashboard; creating one makes them its OWNER.
*   **Server Identity:** Every Minecraft server is tracked via a `server_uuid`.
*   **The Handshake:** Fastify exposes a `/api/v1/register` endpoint to provision `server_uuid`s and `api_key`s for new servers.
*   **Network member management:** Three routes in `routes/v1/networks.ts`, all requiring at least the caller's own `network_members` role via `requireNetworkRole` (`GET` needs MODERATOR — any membership at all; `POST`/`PUT` need ADMIN+): `POST /networks/:networkId/members` (`{ accountId }`) looks the target user up by Account ID (`404` if none), `409`s if they're already a member, otherwise creates a `network_members` row defaulted to MODERATOR — this route only *adds*, a role change is a separate future concern. `GET /networks/:networkId/members` lists every member (`{ userId, name, accountId, role, serverUuids }`), `serverUuids` being that member's `server_access_grants` scoped to *this* network's own servers only (grants carry no `network_id` of their own — the scoping happens by joining through `servers.network_id`). `PUT /networks/:networkId/members/:userId/grants` (`{ serverUuids: [...] }`) replaces, not merges — deletes the member's grants across this network's servers and inserts exactly the given set in one transaction, `400`s if any requested uuid isn't actually one of this network's servers. Grants are only ever *checked* for MODERATOR members (OWNER/ADMIN already get unconditional full server visibility elsewhere) — editing them for an OWNER/ADMIN member is accepted but inert, and `apps/web`'s admin UI simply doesn't expose the permissions modal for non-MODERATOR members. `apps/web`'s `/admin` page and `app/admin/actions.ts` (`addNetworkMember`, `updateMemberGrants`) implement this same logic directly against the DB rather than calling these routes, per the established "web never calls the API" architecture.

## Security & Development Rules
1.  **Strict `.gitignore` Policy:** Sensitive data must never be committed. The `.gitignore` must strictly block `.env`, `.env.local`, `.env.*`, all API keys, database URLs, and TLS/SSL certs.
2.  **API Batching:** Fastify routes handling high-volume data (Command Spy, Ledger) must expect and validate batch JSON arrays.
3.  **Versioning:** Root `package.json`'s `version` field (currently `1.0.0`) is the single source of truth for `GET /api/v1/version`, an unauthenticated endpoint consumed by the iOS app's Settings/Networks screens and the mc-mod's `/pantheon version` command — it reads this file at runtime, nothing hardcodes a duplicate. Standing policy as of 2026-08-14: bump the patch number (the third one) by one on every commit/push to `main`. Never bump major or minor without Sebastian explicitly asking. This applies only to root `package.json` — `apps/api`, `apps/web`, and `packages/db` each carry their own independent (currently stale, unrelated) `version` field that this policy doesn't touch.

## Deployment & Infrastructure Rules
*   **Host Environment:** Self-hosted Proxmox VE server.
*   **Target Container:** Debian/Ubuntu LXC or VM running Docker and Docker Compose.
*   **Database Hosting (production):** PostgreSQL/TimescaleDB is externally hosted on an Oracle Cloud VPS, not a container in `docker-compose.prod.yml` — there is no `postgres` service in prod (unlike `docker-compose.yml`, local dev, which still runs `timescale/timescaledb` locally). `api`/`web` both take `DATABASE_URL` straight from `.env.production` unmodified — nothing in the compose file rewrites it to an internal service name. The Oracle instance needs the `timescaledb` extension installed for the hypertable migrations (`0001`, `0007`) to apply.
*   **Networking & SSL:** Cloudflare Tunnel (`cloudflared`) for securely routing traffic. Transport protocol is pinned to `http2` (TCP) via `command: tunnel --protocol http2 --no-autoupdate run` in `docker-compose.prod.yml` — the default QUIC (UDP) transport was timing out/dropping connections over the Proxmox LXC network path, so http2 trades QUIC's latency benefits for connection stability in this environment.
*   **GitHub Student Pack Tools:** Integrate `@sentry/node` and `@sentry/nextjs` for error tracking. Also **Mailgun** (transactional email — see Authentication & Multi-Tenancy).

## Current State

**Monorepo:** `apps/api` (Fastify), `apps/web` (Next.js 16, App Router, Turbopack), `packages/db` (Drizzle schema + migrations), npm workspaces.

**Database (`packages/db`):** `users`/`accounts`/`sessions`/`verification_tokens` (NextAuth Drizzle adapter shape, extended with `password_hash`, `two_factor_secret`, `two_factor_enabled` — see Authentication & Multi-Tenancy; `users` still has no role column), `networks` (`name`, `owner_id` → `users.id`, `onDelete: restrict` — deleting a user never silently deletes their network), `network_members` (join table: `user_id`, `network_id`, per-network `role` enum `OWNER`/`ADMIN`/`MODERATOR`, composite PK), `servers` (`server_uuid`, `api_key_hash`, `loader_type`, `mc_version`, nullable `network_id` → `networks.id` `onDelete: set null`, unique-indexed on both `server_uuid` and `api_key_hash`), `server_access_grants` (join table: `user_id`, `server_uuid` → `servers.server_uuid` cascade, composite PK — whitelists servers within a network per MODERATOR user), `command_spy_logs` / `ledger_logs` (TimescaleDB hypertables, `occurred_at`-partitioned, 90-day retention). Migrations in `packages/db/drizzle`; migration `0003` is the network-first cutover — adds `networks`/`network_members`/`server_access_grants` and `servers.network_id`, drops `users.role` (column + enum) and `user_servers` entirely; migration `0024` adds the password/2FA columns to `users`; migration `0025` adds `users.account_id` (see Authentication & Multi-Tenancy) as an expand→backfill→contract migration — adds the column nullable, backfills existing rows with a random 8-digit code, *then* sets `NOT NULL` and creates the unique index, since a straight `ADD COLUMN ... NOT NULL` fails outright against a table (`users`) that already has real rows. The hypertable conversion (`0001_timescale_hypertables.sql`) requires the `timescaledb` extension, present on the `timescale/timescaledb` image in `docker-compose.yml` — not on a plain local Postgres.

**API (`apps/api`):**
*   `POST /api/v1/register` — **public handshake**, no auth required. Called directly by the Minecraft server plugin on first boot. Body: `{ name?, loader_type, mc_version }` (snake_case — Java-consumed wire format). Generates `server_uuid` (UUIDv4) and an API key (`ptn_live_` + 32 random bytes), stores only `SHA-256(api_key)` (deterministic — safe for a 256-bit random secret, and enables O(1) lookup by hash), returns `{ server_uuid, api_key, ... }` once. Abuse protection: a route-level rate limit (5 req/10 min per IP, tighter than the app-wide default) plus `trustProxy: true` so per-IP limiting actually works behind the Cloudflare Tunnel instead of bucketing every request under the tunnel's IP.
*   `POST /api/v1/command-spy`, `POST /api/v1/ledger` — batch ingestion (`{ events: [...] }`, 1–500 items, Zod-validated), authenticated via `Authorization: Bearer <api_key>` (looked up by hash — see `plugins/serverAuth.ts`).
*   `POST /api/v1/auth/mobile/discord`, `POST /api/v1/auth/mobile/google`, `POST /api/v1/auth/mobile/register`, `POST /api/v1/auth/mobile/login`, `POST /api/v1/auth/mobile/verify-2fa` (`routes/v1/mobile-auth.ts`) — the native-app counterparts to `apps/web`'s NextAuth flows, all minting/consuming the same NextAuth-JWT session token format `fastify.requireAuth` decodes, so mobile and web sessions are interchangeable. `/discord` does the PKCE code exchange server-side (only place `DISCORD_CLIENT_SECRET` lives) and links/creates the `accounts`+`users` rows itself, since it bypasses NextAuth's adapter entirely. `/google` mirrors `/discord`'s exact find-(link)-or-create logic (`accounts` row for `provider: "google"` wins; else an email match gated on the token's `email_verified` claim; else create fresh), but there's no code exchange at all — the GoogleSignIn-iOS SDK does the whole OAuth dance on-device and hands the app an already-signed ID token, so the route just verifies it server-side (`lib/google.ts`, `google-auth-library`'s `OAuth2Client.verifyIdToken`, audience = `GOOGLE_IOS_CLIENT_ID` — the iOS app's own Google OAuth client, distinct from `apps/web`'s NextAuth `GOOGLE_CLIENT_ID` "Web application" client) and mints a token directly; `503`s until `GOOGLE_IOS_CLIENT_ID` is provisioned, same pattern as `/discord`'s Discord-env-vars check. Neither OAuth route gates on `user.emailVerified` or `user.twoFactorEnabled` — an OAuth provider vouching for the identity makes Pantheon's own verification/2FA gates redundant for that path, which also means **2FA is currently bypassable via either OAuth provider**; a known, accepted asymmetry versus the Credentials path, not yet addressed. `/register` takes `{ name?, email, password }`; `409`s if the email is already taken, otherwise hashes the password, creates the `users` row, writes a 24h verification token into `verification_tokens` (same table/shape apps/web's `/register` writes and apps/web's `GET /verify-email` consumes — this service sends its own copy of the Mailgun email via `lib/mailgun.ts` rather than calling into apps/web, and builds the link against `env.CORS_ORIGIN`), and returns `201` with just `{ user }` — **no session token**, since an unverified account can't sign in via `/login` anyway. `/login` takes `{ email, password }`; on success it either mints a full session token directly, or — if the account has `two_factor_enabled` — returns `{ requiresTwoFactor: true, pendingToken }` (a 5-minute token carrying `{ sub, pending2fa: true }`) instead. `/verify-2fa` takes `{ pendingToken, code }`, decodes and validates the pending token, checks the TOTP code, and mints the real session token. A shared `mintSessionToken()` helper in the same file keeps all five routes' token-minting identical.
*   `GET /api/v1/networks`, `POST /api/v1/networks` (`routes/v1/networks.ts`) — **fully implemented**, used by the iOS app. Both require `Authorization: Bearer <token>` (a NextAuth session token — the same one `/api/v1/auth/mobile/discord` mints) via `fastify.requireAuth`. `GET` returns every network the caller belongs to (`{ id, name, ownerId, role, createdAt }[]`, camelCase — JS/mobile wire format, unlike `/register`'s Java-consumed snake_case) by joining `network_members` → `networks`. `POST` takes `{ name }`, inserts the network and the caller's own `network_members` row with role `OWNER` in one transaction, returns `201` with the created network (`role: "OWNER"`). The rest of `networks.ts` (server list/sessions/leaderboard/command-spy/tardises/ait-log/ledger/antidupe/grieflogger/advancements, server linking/renaming, and the member-management routes below) all sit behind `fastify.requireNetworkRole` — see Authentication & Multi-Tenancy's "Network member management" bullet for the three member routes specifically.
*   `PATCH /api/v1/users/me` (`routes/v1/users.ts`) — `{ name }`, Bearer-authenticated via `fastify.requireAuth`, always acts on the caller (no `:userId` param, nothing to authorize beyond "valid session"). Sets `users.name`, returns the updated user in the same shared `{ id, name, email, accountId }` shape every auth route uses (`mobileAuthUserSchema`) — this is what the mobile app's one-time "Complete Profile" screen and any future profile-editing UI call.
*   `fastify.requireAuth` (`plugins/auth.ts`) decodes a NextAuth JWT forwarded as a Bearer token and re-checks the user still exists in the DB (never trusted from the token alone) — no role check, just authentication. `fastify.requireNetworkRole(minRole)` builds on the same token decoding, additionally reading `:networkId` from the route params and re-checking the caller's `network_members` role — the floor every network-scoped route in `networks.ts` sits behind.
*   `GET /healthz` for container healthchecks.

**Web (`apps/web`):** NextAuth v4, multi-provider — Discord OAuth, Google OAuth, and email/password with optional TOTP 2FA (`@auth/drizzle-adapter`'s `DrizzleAdapter` with a `createUser` override for `account_id` generation — see Authentication & Multi-Tenancy — JWT session strategy so `apps/api` can decode it). shadcn/ui initialized (`components.json`, `Button`/`Card`/`Badge`/`Input`/`Dialog`). The session's `session.user.networks` (`{ id, name, role }[]`) and `name`/`accountId` are all re-derived fresh from the DB on every request inside the `session()` callback (`lib/auth.ts`) — never stale, since the JWT strategy re-runs that callback on each `getServerSession` call, and `name` specifically must never trust the JWT's own cached claim (see the `/complete-profile` guard below). Dashboard (`/`) aggregates servers across every network the user belongs to (`lib/servers.ts`: OWNER/ADMIN see all servers in that network, MODERATOR sees only servers granted via `server_access_grants`); a user with zero network memberships sees a "Create your network" prompt instead (`app/actions.ts#createNetwork`). `/sign-in` offers Discord, Google, and an email/password form (with an inline TOTP step when required) and redirects to `/` if already authenticated; `/register` (now requires a Display Name, not just email/password) + `/register/success` handle Credentials sign-up and the "check your email" confirmation. `src/proxy.ts` (Next 16's renamed `middleware.ts`, Node.js runtime by default) redirects any signed-in request with an empty `users.name` to `/complete-profile` (`app/complete-profile/`) before it reaches any other page — catches both OAuth sign-ins (Discord/Google never collect a name) and pre-existing Credentials accounts from before this system. `TopNav` (`components/top-nav.tsx`, the one piece of chrome present on every authenticated page — this app has no separate sidebar layout) shows the signed-in user's name and formatted Account ID (`lib/account-id-format.ts`'s `formatAccountId`) alongside the nav links. `/admin` (redirects anyone managing zero networks) renders, per network the caller is OWNER/ADMIN of: an unclaimed-servers claim list, an "Add member" form (by Account ID — `app/admin/actions.ts#addNetworkMember`), a full member list (name, formatted Account ID, role badge), and — MODERATOR members only, since grants are inert for OWNER/ADMIN — an "Edit Permissions" modal (`components/edit-permissions-modal.tsx`, a `Dialog` with a server checklist) backed by `updateMemberGrants`, a bulk-replace matching `apps/api`'s `PUT .../grants` semantics exactly. All of `app/admin/actions.ts` independently re-checks the caller's network role — Server Actions are directly POST-reachable regardless of page-level redirects, so the page guard alone isn't sufficient. `/settings` includes a two-factor-authentication section (`components/two-factor-settings.tsx`) alongside sign-out and the version footer.

**Not yet built:** Command Spy / Ledger dashboard views, any use of the ingested event-log data. Also not yet built: a "resend verification email" action (both `/register` paths silently log a Mailgun failure rather than surfacing a retry path); a role-change operation for existing network members (promote/demote between MODERATOR/ADMIN/OWNER) — `POST /networks/:networkId/members` only *adds* new MODERATORs, nothing edits an existing member's role; removing a member from a network entirely (only revoking their per-server grants is wired up).
